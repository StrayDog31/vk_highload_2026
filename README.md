# Tinder

## 1. Тема и целевая аудитория
### 1.1 Тема
Tinder — международное геосоциальное приложение для знакомств, которое позволяет:

- Находить потенциальных партнеров для общения и романтических отношений на основе взаимного интереса
- Использовать механизм свайпов для быстрой оценки профилей
- Обмениваться сообщениями в чате после образования мэтча
- Использовать рекомендательную систему на основе поведения пользователя и машинного обучения

География и покрытие — всемирно.

### 1.2 Функционал MVP
MVP включает в себя:

- Регистрация и авторизация
- Редактирование анкеты
- Карточка анкеты (отображение фото, имени, возраста и краткой информации о пользователе)
- Механика свайпов
- Рекомендательная система
- Чат
- Уведомление о мэтчах

### 1.3 Целевая аудитория

MAU — 75 млн. человек
DAU — 42 млн. человек

Основные регионы:
- США - 35%
- Латинская Америка (Бразилия, Аргентина) - 10%
- Европа - 49%

Средний возраст: 18–35 лет (ядро аудитории — миллениалы и поколение Z)

Гендерное распределение:
- Женщины: 25%
- Мужчины: 75%

### 3.4 Схемы глобальной балансировки
- Latency-based DNS для API и Gateway трафика: DNS-резолвер пользователя направляется на ближайшую точку присутствия на основе геолокации и сетевой задержки. Используется короткий TTL (60 сек), что позволяет быстро перенаправлять пользователей на другие регионы при сбоях или перегрузке ДЦ.
Применение: Домены api.tinder.com, gateway.tinder.com, static.tinder.com

- BGP Anycast + CDN для медиа-трафика: Ключевые домены медиа-инфраструктуры анонсируются из множества точек присутствия CDN-провайдера с использованием Anycast. Пользователь перенаправляется в ближайший узел сети с минимальным числом хопов. Для доставки фото используется распределённая сеть CDN-узлов, что снижает задержки и нагрузку на центральные ДЦ.
Применение: Домен media.tinder.com

### 3.5 Механизмы регулировки трафика между ДЦ
- Active Health Checks: Постоянно выполняются проверки доступности edge-узлов CDN, API-шлюзов и origin-серверов во всех 6 ДЦ. Проверки включают health check эндпойнты (/health) на API-серверах, проверку задержек ответа БД и мониторинг загрузки CPU/сети. При обнаружении деградации или отказа узел автоматически исключается из DNS-выдачи.

- Least Connections: Длительные WS соединения чатов направляются на ДЦ с меньшим количеством подключений.

- Weighted Round-Robin: Использование весовых коэффициентов в глобальном балансировщике нагрузки для управления долями входящего трафика между ДЦ внутри одного региона:

- Client-side Retry Logic: Клиентское приложение хранит список доменов всех 8 ДЦ и способно самостоятельно переключиться на альтернативный регион при недоступности текущего:

## 4 Локальная балансировка нагрузки
### 4.1 Схема балансировки нагрузки
Внутри каждого ДЦ маршрутизация запросов разделена на обработку внешнего и внутреннего трафика.

Внешняя балансировка:

L4 (Транспортный уровень):
Используется SLB LVS.
- Задача: распределение TCP-трафика
- Режим: Direct Routing (DR). Обратный трафик от серверов идет напрямую к клиенту, минуя балансировщик. Это важно для тяжелых изображений и предотвращает перегрузку сети на LVS.
- Резервирование: Active-Active (2 + 1 инстанса), health check каждые 5 секунд
- Количество инстансов: 3 сервера на ДЦ (2 активных + 1 пассивных)

L7 (Прикладной уровень)
Используются серверы NGINX.
- Задача: осуществляют TCP multiplexing, поддерживают WS соединения, выполняют SSL Termination (расшифровку HTTPS).
- Резервирование: Active-Active (2 + 1 инстанса),
- Количество инстансов: 3 сервера NGINX на ДЦ

Внутренняя балансировка:
Для внутреннего трафика ипользуется Envoy Sidecar. Каждый микросервис имеет свой локальный Envoy-прокси, который обеспечивает всю логику взаимодействия с другими сервисами.

- Балансировка между инстансами микросервисов
- Retry при временных ошибках
- Таймауты на запросы
- Сбор метрик (Prometheus)
- Балансировка gRPC-трафика

### 4.2 Рассчет количества балансировщиков
Расчет производится для одного ДЦ на основе пиковых показателей:

| Параметр | 	Значение для US East/EU West |
|-------------|----------------------------|
| Суммарный трафик на 1 ДЦ | 46,7 Гбит/с | 
| Трафик L7 (HTTP + WS, без медиа) | 0,04 Гбит/с |
| Пиковый RPS L7 (HTTP + WS) | 42088 RPS |

Расчет балансировщиков L7 (NGINX)
Для L7 учитываются два ограничителя: пропускная способность и SSL Termination.

По пропускной способности:
- Трафик L7 (текст, уведомления, рекомендации): ~0,04 Гбит/с
- Пропускная способность одного NGINX-сервера: 100 Гбит/с
- 0,04 Гбит/с ÷ 100 Гбит/с = 0,0004 → 1 сервер

По SSL Termination:
- Интенсивность новых TLS-соединений принята равной 30% от общего RPS (с учетом постоянных WebSocket-соединений)
- Пиковый RPS: 42088 RPS × 0,3 = 12626 CPS (connections per second)
- При производительности одного сервера 6 676CPS (из примера):

12626 CPS ÷ 6676 CPS = 1,89 → 2 сервера

Итог для L7:
Выбираем «худший» случай — 2 сервера (по SSL Termination).
С учетом резервирования (N + 1):
2 + 1 = 3 сервера NGINX на один ДЦ

Расчет балансировщиков L4 (LVS)
Ограничителем для L4 выступает только пропускная способность сетевых интерфейсов. Для L4 серверов используются сетевые карты 40GbE.

По пропускной способности: Суммарный трафик на ДЦ: 46,7 Гбит/с
46,7 Гбит/с / 40 Гбит/с = 1,17 → 2 сервера

Итог для L4:
Требуется 2 активных сервера. Применяем формулу резервирования N + 1 (Active-Active):
2 + 1 = 3 сервера LVS на один ДЦ (2 активных + 1 пассивных в горячем резерве)

## 6 Физическая схема БД

### 6.1 Выбор СУБД

### 6.3 Шардирование

| Тип шардирования | Таблицы | Ключ | Обоснование |
|-------------|----------------------------|-------------------------|-------------------------|
| По пользователю | user, photo, session, swipe, push_notification | user_id	| Все данные одного пользователя попадают в один шард, минимизация cross-shard запросов при чтении |
| По паре пользователей | match, chat, messenge | min(user_id1, user_id2)/chat_id | Данные по конкретной паре (матч, чат, сообщения) лежат в одном шарде. Обеспечивает сильную консистентность и быстрые запросы через шарды |
| Георграфическое | user, photo, swipe |	user_id + гео	| Локализация рекомендаций "рядом со мной". Позволяет искать профили только в релевантных гео-шардах. |

В целом, везде применимо рандеву-хэширование.

Если большинство ответов совпало, он получает из Cluster Controller полную текущую конфигурацию кластера |

## 7 Алгоритмы

### 7.1 Рекомендательная система

Рекомендательная система построена как гибридная многослойная архитектура. Вычисления производятся в runtime с использованием существующих таблиц БД (user, swipe, match, photo) и Redis-кэша.

#### 7.1.1 Слой 1: Collaborative Filtering

Используется для поиска похожих пользователей на основе истории лайков из таблицы swipe.

**Алгоритм:**

1. Читаем последние 200 лайков пользователя из FoundationDB: извлекаем записи где creator_id равен текущему пользователю и действие равно like

2. Находим пользователей с похожими лайками (вычисляется в runtime): для каждого кандидата извлекаем его лайки и вычисляем коэффициент Жаккара:
$$\text{similarity}(A, B) = \frac{|\text{likes}_A \cap \text{likes}_B|}{|\text{likes}_A \cup \text{likes}_B|}$$

3. Кэшируем топ-50 похожих пользователей в Redis

4. Для формирования рекомендаций берем профили, которые лайкнули похожие пользователи:

#### 7.1.2 Слой 2: Content-Based Similarity

Вычисляем совместимость профилей на основе био таблицы user. Извлекаем из текстового описания.

**Источники признаков из таблицы user:**
- bio (текстовое описание, из которого извлекаем ключевые слова)
- education (уровень образования)
- occupation (профессия) 
- lifestyle_tags (теги: курение, алкоголь, домашние животные)

**Алгоритм извлечения интересов:**

Для каждого пользователя при первом запросе применяем TF-IDF или простой keyword matching к полю bio для извлечения интересов (например: travel, music, sport). Результат кэшируется в Redis с ключом user:interests:{user_id} и TTL = 24 часа.

#### 7.1.3 Слой 3: Machine Learning Ranking Model

Используется gradient boosting модель (LightGBM) для финального ранжирования кандидатов. Модель обучается на Python, экспортируется в формат **ONNX** и разворачивается в Go сервисе.

Процесс обучения (Python, offline):

1. Собираем обучающую выборку из исторических данных swipe и match
2. Формируем датасет с features (описаны ниже) и target (1 = взаимный мэтч, 0 = нет)
3. Обучаем LightGBM модель на выборке за последние 30 дней
4. Экспортируем модель в формат ONNX для кросс-платформенного использования
5. Деплоим ONNX-модель в Go сервис через ONNX Runtime
6. Переобучение модели: раз в неделю с последующим hot-reload в продакшене

Go-микросервис использует библиотеку ONNX Runtime для загрузки и выполнения модели. Принимает батч из 100 кандидатов с вычисленными features, прогоняет через ONNX-модель, возвращает массив ML_score для каждого профиля. Latency инференса: < 5ms для батча из 100 профилей.

Формат модели: ONNX (Open Neural Network Exchange) — обеспечивает совместимость между Python (обучение) и Go (продакшен), высокую производительность и возможность версионирования.

#### 7.1.4 Решение Cold Start Problem

Для новых пользователей (< 50 свайпов выполнено):

1. При регистрации собираем интересы через теги
2. Используем только слой 4 (интересы из bio), так как нет истории
3. 30% случайных профилей (vs 10% для опытных)
4. Начальный ELO = 1300 (в Redis) первые 7 дней, затем плавно к 1200

#### 7.1.5 Хранилище данных и кэширование

Все промежуточные вычисления кэшируются в **Redis** для снижения нагрузки на PostgreSQL и FoundationDB:

| Ключ Redis | Значение | TTL | Назначение |
|------------|----------|-----|------------|
| user:elo:{user_id} | Целое число (ELO рейтинг) | Нет | Desirability score |
| user:similar:{user_id} | Список похожих пользователей | 1 час | CF кэш |
| user:interests:{user_id} | Список интересов | 24 часа | Content-based |
| user:features:{user_id} | Объект с ML-фичами | 10 минут | Предвычисленные features |
| reco:batch:{user_id} | Список профилей | 5 минут | Готовый батч рекомендаций |

**Источник данных:** Redis (уже указан в п.6.1 и п.8)

### 7.2 Matching Engine

Обработка свайпов и создание мэтчей происходит в реальном времени с использованием транзакционной модели в **FoundationDB**.

Алгоритм обработки свайпа:

1. Пользователь A свайпает вправо (лайк) на профиль B
2. Записываем событие в FoundationDB
3. Проверяем наличие обратного лайка
4. Если обратный лайк существует (взаимный мэтч):
   - Создаем запись в таблице match
   - Создаем чат в таблице chat
   - Отправляем push-уведомления через Kafka обоим пользователям

5. Обновляем ELO-рейтинги в Redis:
   - Асинхронно вычисляем новые ELO
   - Обновляем значения для обоих пользователей
     
Производительность:
- Latency обработки свайпа: < 50ms
- Throughput: 37 000 свайпов/сек (пиковая нагрузка из п.2)
- Источник данных: FoundationDB (swipe), PostgreSQL (match, chat), Redis (ELO), Kafka (уведомления)

## 10 Обеспечение надежности

| Название | Способ обеспечения надежности |
|----------|-------------------------------|
| Nginx | Разворачивается по схеме Active-Passive. Один узел работает как основной, второй - резервный. Если активный выходит из строя, резервный автоматически продолжает обслуживать запросы. Схема резервирования: N+1. |
| Go-сервисы | Graceful shutdown, оркестрация в Kubernetes с автоматическим рестартом. |

| Redis | Redis Cluster с автоматическим шардированием и выбором нового мастера при сбое узла. Двойная персистентность (AOF + RDB). Изоляция сбоев за счёт распределённой топологии и heartbeat-мониторинга. |
| Kafka | Replication Factor = 3, Автоматический перевыбор лидера партиции. Graceful shutdown: флеш log-сегментов на диск и передача лидерства. |
| ScyllaDB | Распределённый кластер с RF=3. Автоматическое восстановление данных, настраиваемый уровень согласованности (consistency level), замена узлов без простоя. |
| ClickHouse | Аналитические данные хранятся в ReplicatedMergeTree с 2 репликами на каждый shard. Graceful shutdown. |
